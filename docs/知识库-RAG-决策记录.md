## 0. 背景与目标

**需求要点（来自你的原话，逐条编号便于对照）：**

1. 菜单「配置」下面新增一个**知识库**（顶栏 tab 切换：知识库管理 / 问答管理）。
2. 知识库管理：新建知识库、导入文档。
3. 导入支持**单个 + 批量**；单个支持 **pdf / md / word / txt**、**手动编辑富文本**、**问答对清单**。
4. 导入后台执行：① 数据识别与清洗（一期只做纯文本）② 分块（三种：固定 / 基于结构 / 基于语义，重叠可配）③ 向量化（可选向量模型，优先云端、纯 custom、统一协议）。导入成功要有提醒。
5. 前端三级结构：**知识库 → 文件夹 → 文档**。检索时知识库与文件夹参与索引匹配；**支持跨文件夹，不支持跨知识库**。
6. 文档页：参考截图样式，但**操作按钮用 SVG 图标（不带文字）**，再加一个**详情**（查看导入时的全部参数：切块策略、实际切块、创建时间等）。
7. 问答管理：数据飞轮。对话页每次调用 RAG 的问答后面带 👍/👎；👎 要填原因。列表展示每次问答的上下文（问答用户 / 原问题 / AI 结果 / 推理过程 / 用户反馈 / 点踩原因 / 问答时间）。支持 **AI 分析（弹窗）**、**筛选（反馈、时间区间）**、**导出**。
8. 检索要支持 **rerank / topk**（配置页也要有）；**AI 不直接输出原文**，而是取回 topk 原文后**自己组织并 rerank 评分**。对话页展示 **最多 5 条**参考结果，**可折叠**。
9. 配置页新增**知识库配置**，承接以上可配项。

**当前代码事实（改造的出发点）：**

- 对话入口：`app.js sendTask()` → IPC `agent:run`（`main.js:1479`）→ `Agent.run()`（`lib/agent.js:1736`）→ 工具循环（`lib/agent-loop.js:444`）。
- 闸门：`Agent._classifyIntent()`（`lib/agent.js:809`）现在输出 `verdict.kind ∈ {chat, engine, route, analysis}`，且在读表前就有 `return`（chat 就地收尾；engine 直接 `_runEngine` 短路）。
- 工具表：`lib/actions.js` 的 `BUILTIN_TOOLS`（sql / describe_table / request_scope / ask_user / load_skill / look_at_data / check_index / read_result / list_workflows / run_workflow / reply / finish）+ MCP 工具。
- 会话状态跨轮携带：`state{tables, schemaMap, fieldsSelected, steps, ...}`，由渲染层持久化并每轮回传。
- 上下文压缩：`lib/agent-loop.js` 的 `compactMessages` + ledger。

## 1. 闸门改造：从「4 选 1 硬分类」到「1 硬位 + 软提示」

**问题**：新增 RAG 后，能力至少 4 种（chat / engine / sql / rag）。若把闸门做成 4 选 1 的硬分类，多轮（你要求 ≥30 轮）必然出问题 —— 混合意图只能选一个、续接轮被重新分类。

**选择**：
- 闸门（`_classifyIntent`）只输出：
  - **硬位** `act`：`'chat'` 或 `'act'`。决定"要不要碰数据库/知识库"。
  - **软提示** `hint = { engine?: string[], rag?: boolean, sql?: boolean }`：只作为 bias 喂进循环，**不作分支**。
- 保留 **engine 唯一高置信命中** 的短路（直接 `_runEngine`，快且确定）；多候选（原 `route`）继续掉进工具循环让模型自己用 `list_workflows` 决定。
- RAG 变成循环里的一个工具 `search_knowledge`，与 `sql` 并列。

**原因**：
- 混合意图（"供应商超期率" = SQL + 制度口径）在同一轮里既调 `sql` 又调 `search_knowledge`，自然解决。
- 多轮续接：模型看得见完整历史与前面所有工具结果，不需要状态机重新分类 —— 这正是代码里把老 `route` 状态机拆掉的理由（`agent.js:1864-1878`）。
- 保留 chat 短路 → 闲聊不碰库、延迟低。

**其他可选方案**：
- (a) 4 选 1 硬分类 —— 否决，理由同上。
- (b) 纯工具化、彻底删掉闸门 —— 否决：闸门换来的是"闲聊零数据库访问"，删掉后每句闲聊都会先读表，且多一次调用并不省。
- (c) `hint` 干脆不要，只留 `act` —— 可接受，但少了给模型的轻量引导；保留为软提示成本极低，故保留。

## 2. RAG 的接入点：两个，不是一个（一期的取舍）

**问题**：RAG 检索接在哪儿？

**选择（一期）**：接在**分析/工具循环**里（`search_knowledge` 工具）。**engine 短路路径一期不接**，列为已知空缺。

**原因**：
- `engine` 短路（`agent.js:1861`）**绕过整个分析段**，天然不会走到工具循环 —— 想让它也带知识，得在 `_runEngine`/`_execEngine` 里单独挂，或给流程卡加"知识节点"。
- 一期的价值密度：分析/route 路径覆盖绝大多数"问数据 + 问口径"的问法。engine 是确定性的取数卡，多数场景不强依赖自由检索。
- 减少一期改动面，避免在两条路径上重复实现 + 重复测试。

**其他可选方案**：
- (a) 一期就在 engine 路径也挂 —— 慢、面大，收益不明。留作二期（"流程卡知识节点"）。
- (b) 把 engine 也改成进循环 —— 否决：会丢掉"高置信直接跑卡"的确定性收益。

## 3. 向量存储

**问题**：向量存哪、怎么查？

**选择**：**本地文件存储 + 暴力余弦检索**，零新依赖。每个知识库一份向量数据（分块向量以 Float32 二进制 + 元数据 JSON 落盘），检索时在**单个知识库内**做全量余弦 + topK。

**原因**：
- 零新依赖（本机离线可跑），契合"桌面端、数据不出本机"的定位。
- 单知识库规模通常几千~几万块，暴力余弦在这个量级完全够用（毫秒级）。
- 你明确要求**不支持跨知识库检索** → 天然可把索引按知识库隔离，进一步简化。

**其他可选方案**：
- (a) sql.js（已在依赖里）建 SQLite + 向量扩展 —— 复杂、wasm 里跑扩展坑多。
- (b) 引入外部向量库（Milvus/Chroma/Qdrant）—— 与"个人桌面"定位冲突、增运维。
- (c) HNSW/IVF 近似索引 —— 这个量级是过度设计；等单库 >10 万块再谈。

**留的接口**：`lib/knowledge/vector.js` 里 `search()` 是唯一检索入口，将来换 ANN 只改这一处。

## 4. 向量化（Embedding）

**问题**：用什么模型、什么协议？

**选择**：**OpenAI 兼容的 `/embeddings` 协议**，`baseURL / apiKey / model` 全可配（"纯 custom"）。内置预设：Qwen/DashScope（`text-embedding-v3` 等）、OpenAI（`text-embedding-3-small/large`）、自定义。请求体统一 `{model, input}`，响应取 `data[].embedding`。

**原因**：
- 与现有 `lib/llm.js` 的 OpenAI 兼容客户端同构，复用同一套"baseURL + key"配置习惯。
- 你要求"优先云端 + 纯 custom + 协议统一" → OpenAI 兼容协议是事实标准，Qwen/DashScope 也提供该协议。
- 不引入本地模型（避免 onnxruntime 之类原生依赖）。

**其他可选方案**：
- (a) 内置本地 embedding（transformers.js / onnxruntime）—— 离线友好，但原生依赖重、体积大，一期不做。留作二期"本地向量模型"。
- (b) 每家 SDK 各写一套 —— 否决，协议不统一。

**一致性问题（已按你的反馈修订）**：向量维度随模型变化。**同一时刻所有文档必须用同一模型、同一维度**。
- **修订**：向量模型与分块策略**统一在「配置 · 知识库」里配**，新建知识库时不再单独选（你的要求）。
- 因此不再按知识库"锁定"一份 embedding —— 导入与检索都读全局配置的当前值，改配置对所有库立即生效。
- 换模型后旧文档维度若不同，检索时会被自动跳过（不报错），需要**重新导入**旧文档才能被新查询命中。UI 上已写明。

## 5. 文档解析（pdf / md / word / txt）

**问题**：四种格式都要支持，但不想引重依赖。

**选择（一期）**：
- **md / txt**：原生直接读，完整支持。
- **word (.docx)**：用**内置 zlib 实现最小 ZIP 读取** → 解 `word/document.xml` → 抽 `<w:t>` 文本。零依赖，能覆盖常见 docx。
- **pdf**：**一期不内建解析器**，改为"**粘贴文本**"入口；导入 pdf 时明确提示"请粘贴文本内容"。
- **富文本**：直接接收 HTML/纯文本，清洗后入库。
- **问答对清单**：接收 `Q/A` 成对（JSON / 两列 TSV / 空行分隔），一条问答 = 一个分块。

**原因**：
- docx 用 zlib 解析 ZIP 是可控的（~150 行），docx 本质是 XML，抽取文本可靠。
- PDF 文本抽取**没有零依赖的可靠实现**（内容流 + 字体映射 + 编码，PDF 是排版格式不是文本格式）。硬写一个"能跑一半"的解析器，产出的是**静默的错误文本**，比明说不支持更糟。
- 一期目标是"链路打通"，文档格式是加分项而非核心。

**其他可选方案**：
- (a) 引入 `pdf-parse` / `mammoth` —— 依赖体积、离线安装风险；且 npm 安装未必可用。留作二期"按需引入"。
- (b) 用外部服务解析 —— 与"数据不出本机"冲突。

**已知空缺**：PDF 需手动粘贴（一期）。文档里明确标注，不假装支持。

## 6. 分块策略

**问题**：三种分块（固定 / 结构 / 语义）怎么实现，重叠怎么算。

**选择**：
- **固定分块**：按字符数切，`size`（默认 800）+ `overlap`（默认 120）可配。按段落边界尽量回退。
- **基于结构**：按 Markdown 标题层级 / 段落切；标题路径作为块的 `section` 元数据。块大小超过上限时回退到固定分块。
- **基于语义**：切成句子 → 逐句调 embedding → 相邻句余弦相似度低于阈值处断句；再按 `maxSize` 合并。阈值可配。
- **重叠**：固定/结构使用字符级 overlap；语义使用"上一块尾句带下一块"作为重叠。

**原因**：三种策略语义清晰、都能独立配置；语义分块天然依赖 embedding，仅在配置了向量模型时可用（否则禁用并提示）。

**其他可选方案**：
- 语义分块用专门的分句模型 —— 过度设计，一期用正则分句 + embedding 相似度即可。

## 7. 检索 + Rerank

**问题**：你要"检索 topk 原文后自己 rerank 评分，不直接吐原文"。

**选择**：
- **两段式**：① 向量召回 `candidateN`（默认 20）② **LLM rerank**：把候选（标题 + 片段）交给模型按相关性打分/筛选，取最终 `topK`（默认 5）。
- **不直接输出原文**：`search_knowledge` 工具返回结构化命中（kbId/folderId/docId/chunkId/score/snippet/section），由模型**自己组织语言**回答；原文只作为模型参考 + 对话页"参考资料"展示。
- `candidateN` / `topK` / `是否 rerank` 都进配置页。

**原因**：直接吐原文 = 没有综合、没有引用意识；rerank 用模型语义判断比纯向量分数更准，尤其是口语化提问。

**其他可选方案**：
- (a) 只做向量 topK 不做 rerank —— 更快，但精度低；做成可关。
- (b) 用专门 rerank 模型（如 gte-rerank）—— 需要额外服务；留作二期（接口已预留 `rerankMode: 'llm' | 'model'`）。

## 8. 知识库 / 文件夹 / 文档 三级结构与检索范围

**问题**：三级结构 + "跨文件夹可、跨知识库不可"。

**选择**：
- 磁盘结构：`userData/knowledge/<kbId>/{kb.json, folders.json, docs/<docId>.json, vectors/<docId>.bin, chunks/<docId>.json}`。
- 检索**永远限定在单个知识库内**；知识库内的文件夹**默认可跨**（folderId 作为元数据参与排序加权，不设墙）。
- 对话页新增**知识库选择器**（跟数据库选择器同款 `.pick` 下拉，**多选**），和"选库"胶囊同一行；默认库可在配置页设。

**多选修订（按反馈）**：选择器支持多选。多选时 `search_knowledge` 走 `searchMany` —— **每个库各自召回，合并候选后统一 rerank**。这不是"把多个库的向量混进一个索引"（那仍不支持），而是多路检索后汇总排序。空选 = 用配置里的默认库（没设默认则搜全部库）。

**原因**：你明确"不支持跨知识库索引"。文件系统隔离最直观；知识库选择器让"查哪个库"显式可控。

**其他可选方案**：
- 检索时让模型自己选库 —— 一期先做显式选择器，更可预测；后续可加"自动选库"。

## 9. 问答管理（数据飞轮）

**问题**：怎么记录、筛选、分析、导出。

**选择**：
- **记录**：每次调用了 RAG 的问答，落一条记录（append-only JSONL，按知识库或全局）。字段：`id, ts, userId(默认'本机用户'), kbIds, question, answer, reasoning, ragHits[{docId,chunkId,score,title}], feedback(null|'up'|'down'), feedbackReason{tags[], text}, model, latencyMs, usage`。
- **反馈**：对话页该条回答下 👍/👎；👎 弹原因（标签：有害/不安全、虚假信息、没有帮助、其他 + 自由文本）—— 对齐你给的反馈截图。
- **列表**：时间倒序，展示上下文全字段。
- **筛选**：反馈类型、时间区间、（扩展位）知识库、关键词。
- **AI 分析**：把选中/筛选出的记录摘要交给 LLM，产出"共性点踩原因 / 知识库缺口 / 改进建议"，**弹窗展示**。
- **导出**：JSONL / CSV。

**原因**：JSONL append-only 简单、抗损坏、易导出；字段面向"飞轮"（哪类问题答不好 → 补文档 → 再测）。

**其他可选方案**：
- 存 SQLite —— 查询强，但引入 sql.js 的落盘复杂度；一期 JSONL 够用。

## 12. 取舍与已知空缺（一期不做，写明）

| 项 | 一期 | 原因 |
|---|---|---|
| PDF 解析 | ❌ 改"粘贴文本" | 无零依赖可靠实现，硬做产出静默错误 |
| engine 短路路径带知识 | ❌ | 需另挂接入点，二期做"流程卡知识节点" |
| 本地 embedding 模型 | ❌ | 原生依赖重 |
| ANN 近似索引 | ❌ | 当前规模暴力余弦足够 |
| 专门 rerank 模型 | ❌（接口预留） | 需额外服务 |
| 多用户/权限 | ❌（用户默认"本机用户"） | 你说明用户系统暂未做 |
| 语义分块 | ✅（需配置向量模型） | 依赖 embedding，未配则禁用 |
